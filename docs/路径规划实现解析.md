# OptiRoute-LastMile 路径规划实现解析

这份文档面向“想读懂项目代码的人”，目标不是只告诉你项目用了什么算法，而是把这套路径规划在代码里到底怎么跑起来讲清楚。读完后，你应该能回答这几个问题：

- 一次“开始调度”到底触发了哪些代码。
- K-Means 在这个项目里具体负责什么。
- 遗传算法在这个项目里具体负责什么。
- 后端如何把中间结果和最终结果存进数据库。
- 前端为什么能一边轮询一边看到路径逐步出现。

## 1. 先说结论

这个项目的“路径规划”不是一个单一算法，而是一个两阶段启发式流程：

1. **先分区**：用带约束的 K-Means，把待配送包裹分给不同快递员。
2. **再排顺序**：对每个快递员分到的那一组地址，用遗传算法求一个近似最优访问顺序。

可以把它理解成两个不同层面的问题：

- **问题 A：谁送哪些包裹？**
  这是聚类问题，由 `ConstrainedKMeans` 负责。
- **问题 B：已经确定某个快递员送这些包裹后，先送谁后送谁？**
  这是 TSP 风格问题，由 `GeneticAlgorithmTSP` 负责。

项目主流程入口可以直接看这几个文件：

- `backend/app/api/v1/endpoints/dispatch.py`
- `backend/app/services/dispatch_service.py`
- `backend/app/core/algorithms/kmeans.py`
- `backend/app/core/algorithms/genetic.py`
- `frontend/src/views/SmartDispatch.vue`

## 2. 你应该先建立的业务模型

在理解算法之前，先理解数据对象。这个项目的路径规划围绕 5 个核心模型展开，定义在 `backend/app/models/all_models.py`。

### 2.1 DeliveryStation

配送站，算法中的“仓库 / 起终点 / depot”。

- 一个调度计划只对应一个站点。
- 每条路线默认都从站点出发，再回到站点。

### 2.2 Courier

快递员，算法中的“车辆 / 运力单位”。

关键字段：

- `status`：只有 `AVAILABLE` 的快递员会参与调度。
- `max_capacity`：最大载重，是聚类阶段的重要约束。
- `station_id`：当前隶属哪个站点。

### 2.3 Package

包裹，算法中的“待访问点 / demand point”。

关键字段：

- `latitude`、`longitude`：收件点坐标。
- `weight`：参与载重约束。
- `status`：只有 `PENDING` 的包裹会进入本次调度。
- `route_id`：调度完成后会绑定到某条路线。

### 2.4 DeliveryPlan

一次调度任务。

关键字段：

- `status`：`OPTIMIZING -> READY/COMPLETED`
- `algorithm_meta`：保存部分算法元数据
- `routes`：该计划生成的所有路线

### 2.5 DeliveryRoute

一次计划中的单条路线，通常对应一个快递员。

关键字段：

- `courier_id`
- `total_distance`
- `geo_json`

其中 `geo_json` 很重要，因为前端地图几乎完全靠它渲染。

## 3. 一次调度是怎么跑起来的

### 3.1 前端发起调度

前端页面在 `frontend/src/views/SmartDispatch.vue`。

点击“开始调度”后，`startDispatch()` 会执行：

1. 检查是否有 `PENDING` 包裹和 `AVAILABLE` 快递员。
2. 检查当前主站点是否加载完成。
3. 向 `/api/v1/dispatch/plans` 发送 POST 请求。

请求体非常简单：

```json
{
  "title": "调度计划 2026/4/5 ...",
  "station_id": 3
}
```

这里有个值得注意的点：

- 前端**不会**把聚类数、GA 代数、种群规模这些“调参项”发给后端。
- 这些参数目前都写死在后端代码里。

这是前端测试里也明确验证过的行为。

### 3.2 后端创建计划并启动后台任务

`backend/app/api/v1/endpoints/dispatch.py` 里的 `create_dispatch_plan()` 做三件事：

1. 检查 `station_id` 对应的站点是否存在。
2. 创建 `DeliveryPlan`，初始状态设为 `OPTIMIZING`。
3. 通过 `BackgroundTasks` 启动 `run_dispatch_background(plan_id)`。

这一步很重要，因为它说明：

- HTTP 请求本身不等待整个算法跑完。
- 前端拿到 `plan_id` 后，会进入轮询模式。

### 3.3 后台线程真正执行调度

`run_dispatch_background()` 会新建一个数据库 session，然后调用：

```python
DispatchService(db).run_dispatch_algorithm(plan_id)
```

也就是说，真正的算法 orchestration 在 `DispatchService` 里。

## 4. 调度服务是整个实现的中枢

`backend/app/services/dispatch_service.py` 是最关键的文件。你可以把它当成“算法编排器”。

它的执行顺序基本如下：

```text
读取 plan
-> 找站点
-> 取待配送包裹
-> 取可用快递员
-> 跑约束 K-Means
-> 为每个 cluster 预建 route
-> 对每个 cluster 跑 GA
-> 回写 package / route / plan
```

下面按代码逻辑展开。

### 4.1 加载输入数据

`run_dispatch_algorithm()` 首先读取：

- 当前计划 `plan`
- 计划对应的 `station`
- 所有 `PENDING` 的包裹
- 该站点下所有 `AVAILABLE` 的快递员

这里有一个实现细节很值得注意：

- 包裹查询只按 `status == PENDING` 过滤。
- 它**没有按站点过滤包裹**。

在当前项目里因为主站点模式较强、演示数据也围绕当前站点生成，所以通常不会暴露问题；但从工程角度看，这意味着如果以后做多站点，这里要改。

### 4.2 处理空输入

如果没有待配送包裹，或者没有可用快递员，计划会直接结束：

- `plan.status = COMPLETED`
- `plan.algorithm_meta = {"error": "..."}`

所以这个项目里 `COMPLETED` 不一定表示“成功调度完成”，也可能表示“流程结束但没有可算的数据”。

### 4.3 决定聚类数 k

代码逻辑是：

```python
k = min(num_couriers, num_packages)
```

这表示：

- 最多每个包裹一个 cluster，但没有意义，所以不能超过包裹数。
- 通常更接近“每个可用快递员对应一个 cluster”。

### 4.4 准备 K-Means 输入

服务层会把 ORM 模型转换成算法输入：

- `recipient_coords = [(p.latitude, p.longitude), ...]`
- `weights = [p.weight, ...]`
- `depot_coord = (station.latitude, station.longitude)`
- `courier_capacities = [c.max_capacity, ...]`

这里项目内部大多数算法代码都使用：

- **内部坐标顺序：`(lat, lon)`**

但写入 `geo_json` 时，又会转换成：

- **前端渲染顺序：`[lon, lat]`**

这个顺序差异是理解整个项目最容易踩坑的地方之一。

### 4.5 跑带约束的 K-Means

实际调用是：

```python
kmeans = ConstrainedKMeans(k=k, max_distance_from_depot=50.0)
kmeans.fit(recipient_coords, depot_coord, weights=weights, courier_capacities=courier_capacities)
clusters = kmeans.get_clusters(recipient_coords)
```

这里的固定参数：

- `max_distance_from_depot = 50.0 km`

聚类完成后，计划会先记录一份中间元数据：

```python
plan.algorithm_meta = {
    "step": "k_means_done",
    "clusters": clusters
}
```

说明当前系统的 `algorithm_meta` 主要保存了聚类结果，而不是完整的 GA 历史。

### 4.6 为每个 cluster 预创建路线对象

在真正跑 GA 之前，服务层会先创建 `DeliveryRoute`：

- `plan_id` 绑定到当前计划
- `courier_id` 绑定到对应快递员
- `geo_json = {"status": "calculating"}`

这一步的作用是：

- 提前在数据库里有 route 记录
- 后续 GA 迭代时可以不断更新这条 route 的 `geo_json`
- 前端轮询时就能看到“渐进中的路线”

这里快递员和聚类的绑定方式非常直接：

```python
courier = couriers[cluster_idx]
```

也就是说：

- cluster 0 对应快递员列表里的第 0 个
- cluster 1 对应第 1 个
- ...

这不是全局最优匹配，只是一个简单映射。

### 4.7 对每个 cluster 跑 GA

每个 cluster 会被单独处理：

1. 拿到该 cluster 的包裹列表
2. 计算 cluster 的几何中心
3. 构造 GA 进度回调
4. 调用遗传算法求解访问顺序
5. 回写最终路径

也就是说，整个系统的优化顺序是：

- 先把大问题拆成多个子问题
- 再对子问题逐个求近似解

它不是同时做“分组 + 排序 + 司机匹配”的统一优化模型。

### 4.8 GA 进度如何实时显示

`DispatchService` 里定义了 `ga_progress_callback()`。这个回调会把当前最好解写进 `route.geo_json`，字段包括：

- `type: "LineString"`
- `coordinates`
- `cluster_center`
- `total_distance_km`
- `package_count`
- `total_weight`
- `color`
- `generation`
- `status: "optimizing"`
- `packages_ordered`

并且每 20 代 commit 一次数据库。

这就是前端为什么能在轮询时看到“路线正在慢慢成形”的根本原因。

这个做法非常适合演示系统，但不一定适合生产：

- commit 频率较高
- 依赖轮询数据库
- 更高并发下可能有性能压力

### 4.9 写入最终结果

GA 返回的是一个索引顺序，例如：

```python
[2, 0, 1, 3]
```

它表示“按这个顺序访问 cluster 内的包裹”。

服务层会据此：

1. 给对应包裹设置 `route_id`
2. 把包裹状态改成 `ASSIGNED`
3. 重新计算最终总里程
4. 把 `route.geo_json.status` 改成 `optimized`
5. 把 `route.total_distance` 写入数据库

全部 cluster 完成后：

- `plan.status = READY`

这时前端轮询到 `READY`，就会停止轮询并显示最终结果。

## 5. 第一阶段：约束 K-Means 到底怎么实现

代码在 `backend/app/core/algorithms/kmeans.py`。

这个文件不是调用第三方 K-Means，而是自己实现了一套“带容量和站点约束的 K-Means 变体”。

## 5.1 为什么这里不用普通 K-Means

普通 K-Means 只关心“空间上离哪个中心更近”，不关心：

- 快递员有没有超载
- 聚类中心是否离配送站太远

而配送场景至少有两个现实限制：

1. 每个快递员有载重上限。
2. 每个片区不能离站点过远，否则调度结果会失真。

所以项目实现了自己的约束逻辑。

### 5.2 距离计算

项目使用的是 **Haversine 距离**，也就是球面直线距离近似。

有两套实现：

- 标量版：`haversine_distance()`
- 向量化版：`haversine_vectorized()`

向量化版本主要用于批量计算点到质心的距离矩阵，提高性能。

### 5.3 初始化聚类中心

`initialize_centroids_around_depot()` 不会随机在全地图上初始化中心，而是：

- 以 depot 为圆心
- 在一个默认 `5km` 半径内
- 随机生成 `k` 个初始中心

这样做的直觉是：

- 配送任务本来就围绕站点展开
- 从站点附近开始初始化，通常比完全随机更贴近业务

### 5.4 核心循环

`fit()` 的主循环是标准 K-Means 的骨架：

1. 记录上一轮中心
2. 给每个点分配 cluster
3. 更新 cluster 中心
4. 判断是否收敛

但其中第 2 步和第 3 步都加入了业务约束。

### 5.5 带容量约束的分配策略

最关键的逻辑在 `_assign_points_capacitated()`。

先做几件事：

1. 计算每个点到每个中心的距离矩阵。
2. 对每个点把所有 cluster 按距离从近到远排序。
3. 计算每个点的“遗憾值（regret）”。

遗憾值的定义是：

```text
次优距离 - 最优距离
```

如果一个点的遗憾值很大，说明：

- 它特别适合某一个 cluster
- 一旦不能分给最优 cluster，损失会很大

所以代码会按遗憾值从大到小处理点，优先满足这些“难安排”的点。

这是这套实现里非常值得学习的一点，因为它不是简单地“所有点各自找最近中心”，而是试图减少后续冲突。

### 5.6 容量约束怎么生效

对每个点，算法会按偏好顺序尝试 cluster：

```python
if current_loads[cluster_idx] + point_weight <= capacities[cluster_idx]:
    assign
```

只有不超载时才允许分配。

如果首选 cluster 满了，就尝试次优、再次优。

### 5.7 如果所有 cluster 都装不下怎么办

这里有一个非常现实的 fallback：

1. 再次检查所有 cluster，看看是否还有能塞下的。
2. 如果仍然没有，就把这个点分给“剩余容量最多”的 cluster。

这意味着：

- 这套实现**不是绝对硬约束**。
- 当总容量不足或容量碎片化时，它会接受“少量超载”，而不是直接失败。

这是一个工程取舍：

- 好处：调度流程尽量能给出结果。
- 代价：理论上可能出现超载 cluster。

项目的演示数据生成逻辑会尽量避免走到这个分支，后面会讲。

### 5.8 聚类中心的站点距离约束

`update_centroids_with_constraint()` 在更新 cluster 中心时，会先求该 cluster 点集的平均值，然后检查它离 depot 是否超过 `max_dist`。

如果超过，就把中心沿着“depot -> centroid”的方向拉回边界上。

所以这里的约束是：

- **约束的是 cluster 中心**
- **不是直接删除远点**

这点很重要。它并不会说“离站点太远的包裹不能配送”，而是说“聚类中心不要跑得离站点太远”。

### 5.9 收敛条件

如果这一轮中心移动量小于 `tolerance`，就停止迭代。

默认参数：

- `max_iterations = 100`
- `tolerance = 1e-4`

### 5.10 输出结果

K-Means 最终产出：

- `self.labels`
- `self.centroids`
- `self.inertia`
- `get_clusters()` 生成的 `{cluster_id: [package_index, ...]}`

服务层真正使用的是 `get_clusters()`。

## 6. 第二阶段：遗传算法如何给每个 cluster 排访问顺序

代码在 `backend/app/core/algorithms/genetic.py`。

这里解决的是一个简化 TSP：

- 起点是 depot
- 中间访问 cluster 内所有包裹
- 最后回到 depot

### 6.1 染色体怎么表示

一条染色体本质上是一个排列：

```python
[3, 1, 0, 2]
```

表示按这个顺序访问 cluster 内的 4 个点。

### 6.2 适应度函数

适应度定义为：

```python
fitness = 1 / (total_distance + 1e-6)
```

也就是说：

- 路越短，fitness 越大
- 遗传算法因此会倾向保留短路径

路径总距离的计算方式是：

```text
depot -> 点1 -> 点2 -> ... -> 点N -> depot
```

同样使用 Haversine 距离。

### 6.3 初始化种群

`_initialize_population()` 会生成很多随机排列。

例如有 6 个点时，每个个体都是 `0..5` 的一个乱序。

这个阶段没有启发式构造初始解，完全依赖随机初始化。

### 6.4 每一代做什么

`solve()` 的每一代大致顺序如下：

1. 计算全体个体的 fitness
2. 找出当前最优个体
3. 对当前最优个体做一次 `2-opt` 局部搜索
4. 更新全局最优解
5. 如果长期没有提升，就调高变异率
6. 用精英保留 + 锦标赛选择 + 交叉 + 变异 生成下一代

### 6.5 2-opt 局部搜索

这一步很关键，因为它让算法不只是“纯 GA”，而是“GA + 局部改良”。

`_two_opt_search()` 的做法是：

- 选择一个区间 `[i:j]`
- 把这段路径反转
- 如果新路线更短，就接受

这相当于对 GA 当前找到的好解再做一次局部打磨。

可以把它理解成：

- GA 负责全局探索
- 2-opt 负责局部修边

### 6.6 自适应变异

如果 20 代都没有更好的全局最优解，代码会提高变异率：

```python
current_mutation_rate = min(0.5, current_mutation_rate * 1.5)
```

目的很直接：

- 避免过早收敛
- 让种群跳出局部最优

一旦找到更好解，又恢复到基准变异率。

### 6.7 选择、交叉、变异

这套 GA 组合用了几种经典操作：

- **锦标赛选择**：`_tournament_selection()`
- **顺序交叉 OX1**：`_order_crossover()`
- **交换变异**：`_swap_mutation()`
- **精英保留**：保留当前最好的一部分个体

这是一个很常见、也比较稳妥的排列编码 GA 组合。

### 6.8 GA 为什么能“实时出图”

`solve()` 每 5 代会调用一次 `progress_callback`：

```python
if progress_callback and generation % 5 == 0:
    progress_callback(...)
```

而服务层收到这个回调后，会把当前最好路径写进数据库。

所以：

- GA 在算
- 后端在把中间最好解刷到 route
- 前端在轮询 route

三者连起来，就形成了“动态优化中”的体验。

## 7. 前端是怎么把算法结果画出来的

这个项目前端的重点不是参与优化，而是消费优化结果。

### 7.1 轮询机制

`SmartDispatch.vue` 在创建计划后，会每秒请求一次：

```text
GET /api/v1/dispatch/plans/{plan_id}
```

一旦响应里带有 `routes`，前端就开始画线。

如果计划状态变成：

- `READY`
- `COMPLETED`

轮询就停止。

### 7.2 前端使用的路线数据格式

后端写入的 `route.geo_json` 大致长这样：

```json
{
  "type": "LineString",
  "coordinates": [[121.47, 31.23], [121.48, 31.24], [121.47, 31.23]],
  "cluster_center": [31.24, 121.48],
  "total_distance_km": 12.6,
  "package_count": 8,
  "total_weight": 18.5,
  "color": "#667eea",
  "generation": 40,
  "status": "optimizing",
  "packages_ordered": [...]
}
```

几个关键点：

- `coordinates` 用的是 `[lon, lat]`
- `cluster_center` 用的是 `[lat, lon]`
- `generation` 只有优化中间态会频繁更新
- `packages_ordered` 让前端可以给每个站点标注“第几站”

### 7.3 地图层做了什么

前端拿到 routes 后会：

1. 把折线画出来
2. 给每个包裹点打顺序编号 marker
3. 用 `cluster_center` 画一个半透明圆，表示分区范围
4. 汇总所有路线总距离
5. 取最大的 `generation` 作为“当前迭代代数”

所以前端显示的“最新迭代”并不是整个系统统一的 GA 代数，而是：

- 当前所有 route 中 `generation` 的最大值

## 8. 为什么演示数据通常能算出结果

`/api/v1/dispatch/reset-demo` 不是单纯随机造数据，它其实在为算法“铺路”。

关键逻辑在 `backend/app/api/v1/endpoints/dispatch.py` 和 `backend/app/services/demo_data_service.py`。

### 8.1 包裹怎么生成

包裹会围绕当前站点在一个约 `0-15km` 的圆盘里生成。

这意味着：

- 样本整体围绕 depot 分布
- 不会出现特别离谱的超远点

### 8.2 快递员容量怎么生成

系统会先算出被选中 `PENDING` 包裹的总重量，然后：

1. 随机激活一批快递员
2. 把每个快递员容量设为“期望平均载重的 1.1x - 1.4x”
3. 如果总容量还不够，就继续加人
4. 如果没人可加，就直接给已有快递员加容量

所以这个演示系统实际上在尽量保证：

- 总容量大于总需求

这会显著降低 K-Means fallback 超载分配的概率。

## 9. 当前实现里最值得你留意的几个工程细节

### 9.1 这是“分而治之”，不是全局最优模型

整个系统先聚类，再对每个 cluster 做局部路径优化。

这意味着它优化的是：

- 先让分区尽量合理
- 再让每个分区内部路径尽量短

它**没有**同时联合优化：

- 包裹分配
- 快递员匹配
- 路线排序

所以这套实现更像工程上可落地的启发式，而不是严格求全局最优。

### 9.2 快递员和 cluster 的绑定很简单

当前绑定方式是按索引硬配：

- 第 0 个 cluster -> 第 0 个快递员
- 第 1 个 cluster -> 第 1 个快递员

它没有进一步考虑：

- 哪个快递员更适合哪个片区
- 历史负载
- 经验等级
- 回站时间

### 9.3 距离不是道路距离

整个项目目前都用 Haversine 直线距离。

这会带来两个结果：

1. 算法更简单、更快。
2. 结果更适合演示，不适合直接当真实导航路径。

所以你在地图上看到的是“优化顺序”和“示意路线”，不是精确道路导航。

### 9.4 中间结果存库是为了演示体验

GA 中间过程不断 commit 到数据库，这能做出“实时刷新”效果，但严格说这是为了演示而做的工程折中。

如果做生产系统，通常会考虑：

- WebSocket
- Redis / 队列
- 更细粒度的任务状态流

### 9.5 `algorithm_meta` 记录得不完整

从字段命名看，你可能会以为它会记录完整算法配置和历史，但当前实现主要只保存：

- K-Means 完成后的 cluster 映射
- 或错误信息

GA 的参数、每代 fitness 历史、最终使用的配置并没有完整持久化。

### 9.6 坐标顺序必须反复确认

项目里同时存在两种坐标表达：

- 算法内部：`(lat, lon)`
- 路线输出：`[lon, lat]`

如果你以后改地图、改 GeoJSON、接入真实路网，这里非常容易出错。

## 10. 建议你按什么顺序读源码

如果你准备自己继续深挖，我建议按下面顺序读：

1. `frontend/src/views/SmartDispatch.vue`
   先理解用户操作、轮询和地图展示。
2. `backend/app/api/v1/endpoints/dispatch.py`
   理解 HTTP 接口如何创建计划和触发后台任务。
3. `backend/app/services/dispatch_service.py`
   理解整个调度编排。
4. `backend/app/core/algorithms/kmeans.py`

5. `backend/app/core/algorithms/genetic.py`

   用测试帮助你验证自己是否理解了算法行为。

## 11. 如果你想继续学，可以重点做这几个练习

### 练习 1：打印每个 cluster 的总重量

在 `DispatchService` 里打印每个 cluster 的：

- 包裹数
- 总重量
- 对应快递员容量

这能帮助你真正理解“K-Means 结果是否合理”。

### 练习 2：调小或调大 `max_distance_from_depot`

把 `50.0` 改成更小或更大，观察：

- cluster 形状是否变化
- 总距离是否变化
- 是否更容易出现不合理分区

### 练习 3：记录 GA 的 fitness 历史

把 `fitness_history` 写到 `algorithm_meta` 或单独字段里，再在前端画出收敛曲线。

这样你就能看到：

- GA 是否真的在收敛
- 哪些数据集更难优化

### 练习 4：把快递员匹配从“按索引”改成“按容量排序”

例如：

- 大 cluster 优先分给大容量快递员

这会让你更深入理解“聚类输出”和“快递员绑定”其实是两个不同问题。

### 练习 5：引入道路距离矩阵

如果后面你想做更真实的路径规划，可以把：

- Haversine 直线距离

替换成：

- 外部地图服务返回的道路距离 / 时间矩阵

那时这套项目就会从“演示级调度”更接近“可运营调度”。

## 12. 你可以怎么理解这套项目

如果用一句话总结：

> 这个项目把“末端配送路径规划”拆成了“先按载重与空间位置分组，再在组内做近似最短路径搜索”的两阶段系统，并通过数据库持久化中间结果，让前端能够实时回放优化过程。

如果再用更通俗的话说：

- K-Means 决定“每个快递员负责哪一片”
- GA 决定“这片里的地址按什么顺序跑”
- `DispatchService` 决定“整个系统按什么顺序把这两件事串起来”
- `SmartDispatch.vue` 决定“怎么把这个过程展示给你看”
