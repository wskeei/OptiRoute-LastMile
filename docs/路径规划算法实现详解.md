# OptiRoute-LastMile 路径规划算法实现详解

这份文档只做一件事：把这个项目的路径规划算法讲透。

重点不是“页面怎么点”，也不是“接口怎么调”，而是下面这些核心问题：

- 这个项目到底在求解什么数学问题。
- 为什么它没有直接求一个完整的 VRP，而是拆成两步。
- 第一步约束 K-Means 是怎么分包裹的。
- 第二步遗传算法是怎么排访问顺序的。
- 这两步在项目代码里是怎么衔接起来的。
- 这套实现的优点、代价和局限分别是什么。

如果你想真正读懂这个项目的路径规划，这份文档应该比“按业务流程散着讲”更适合。

---

## 1. 先建立一个正确的问题视角

### 1.1 这个项目本质上在解决什么问题

从业务上看，它在做“末端配送调度”。

从算法上看，它想解决的是一个接近 **CVRP（Capacitated Vehicle Routing Problem，带容量约束的车辆路径问题）** 的问题：

- 有一个配送站 `depot`
- 有很多待送包裹 `packages`
- 有若干可用快递员 `couriers`
- 每个快递员有容量上限
- 每个包裹有重量
- 目标是把包裹分配给快递员，并确定每个快递员的配送顺序，使总配送成本尽量小

如果把它写成一句更算法化的话：

> 在单仓库、多个配送点、多个运力单位、带载重约束的条件下，最小化整体路线成本。

### 1.2 为什么项目没有直接求“标准 CVRP”

因为标准 CVRP 是组合优化难题。

它同时包含三类决策：

1. **分配决策**：每个包裹给谁送
2. **排序决策**：这个快递员先送哪个，再送哪个
3. **约束决策**：每个快递员不能超载，路线通常要从站点出发再回站点

如果把这三件事一次性联合求最优，复杂度会很高。对一个教学/演示项目来说，通常不会直接上：

- 精确整数规划
- 列生成
- 大规模禁忌搜索 / ALNS / LKH 级别求解器

所以这个项目采用了一个非常典型的工程化策略：

## 先拆问题，再分别求近似解

它把原问题拆成两步：

### 第一步：空间分区 + 容量约束分配

回答的问题是：

> 这些包裹大致应该由哪些快递员负责？

这里用的是 **带约束的 K-Means**。

### 第二步：单条路线内部排序

回答的问题是：

> 对于某个快递员已经拿到的这一批包裹，访问顺序应该是什么？

这里用的是 **遗传算法求 TSP 风格路线**。

所以你可以把项目当前算法概括为：

> 用聚类近似“分车 / 分片区”，再用 TSP 近似“片区内最短访问顺序”。

## 2. 整体算法架构：这是一个“两阶段启发式”

核心入口在：

- `backend/app/services/dispatch_service.py`

其中真正的算法主线在 `run_dispatch_algorithm(plan_id)`。

如果把这段代码抽象成伪代码，大致是这样：

```text
输入:
  depot = 当前站点
  P = 所有待配送包裹
  C = 所有可用快递员

步骤 1: 确定聚类数 k
  k = min(|C|, |P|)

步骤 2: 用约束 K-Means 把 P 分成 k 组
  clusters = cluster(P, depot, package_weights, courier_capacities)

步骤 3: 对每个 cluster 单独求解 TSP 风格路线
  for each cluster_i in clusters:
      route_i = GA_TSP(cluster_i.points, depot)

步骤 4: 写回数据库
  保存每条 route 的几何信息、总距离、包裹顺序
```

这就是这个项目的算法骨架。

### 2.1 为什么这种拆法有效

因为现实里的配送问题天然有两个层次：

#### 层次 A：区域划分

先决定哪些点应该归为同一条路线。

如果这一步做得合理，通常会得到：

- 同一条路线上的点空间上比较接近
- 每条路线的载重量比较平衡
- 每个快递员负责的区域更自然

#### 层次 B：区域内排序

在已经确定一条路线要覆盖哪些点后，再去求：

- 哪个访问顺序更短

这样，原本一个很难的全局问题，被拆成了：

- 一个“带容量的聚类问题”
- 多个“小规模 TSP 问题”

这不是全局最优，但通常是一个合理、可实现、易讲解的工程方案。

## 3. 这个项目求解时到底有哪些输入

在 `DispatchService.run_dispatch_algorithm()` 里，算法读取的输入可以抽象成 4 类。

### 3.1 配送站 depot

来自当前 `plan.station`。

在算法里它有两个角色：

1. 所有路线的起点和终点
2. 聚类初始化和聚类约束的参考中心

项目里统一记作：

```python
depot_coord = (station.latitude, station.longitude)
```

注意这里内部坐标顺序是：

- `(lat, lon)`

### 3.2 待调度包裹 packages

当前代码取的是：

```python
models.Package.status == PENDING
```

然后抽取出算法需要的字段：

- 坐标 `(latitude, longitude)`
- 重量 `weight`

转成：

```python
recipient_coords = [(p.latitude, p.longitude) for p in packages]
weights = [p.weight for p in packages]
```

### 3.3 可用快递员 couriers

当前代码取的是：

```python
models.Courier.station_id == station.id
models.Courier.status == AVAILABLE
```

算法真正关心的是它们的容量：

```python
courier_capacities = [c.max_capacity for c in couriers]
```

### 3.4 聚类数 k

代码中写死为：

```python
k = min(num_couriers, num_packages)
```

含义是：

- 不会比包裹数更多
- 通常接近“一个快递员一个 cluster”

这其实对应一种假设：

> 当前调度里，每个可用快递员大致生成一条路线。

## 4. 第一阶段：约束 K-Means 到底在解决什么

代码在：

- `backend/app/core/algorithms/kmeans.py`

这一步不是在求完整路径，而是在回答：

> 每个包裹应该分给哪条路线、哪位快递员？

### 4.1 普通 K-Means 会做什么

如果没有任何业务约束，普通 K-Means 的逻辑很简单：

1. 初始化 `k` 个中心
2. 每个点分给最近的中心
3. 每个中心更新为其点集均值
4. 重复直到收敛

它优化的是：

> 让点到所属中心的距离尽量小

如果只考虑空间紧凑性，K-Means 很适合拿来做“按片区划分任务”。

### 4.2 但普通 K-Means 不够

在配送场景里，单纯按空间最近分组不够，因为它会忽略两个关键现实约束：

#### 约束 1：快递员容量有限

如果三个重包裹刚好挨得很近，普通 K-Means 会倾向把它们分进同一个 cluster。

但现实中可能：

- 三个包裹总重 30kg
- 对应快递员最大载重只有 20kg

那这条路线就不可执行。

#### 约束 2：片区不能离站点太远

如果某个聚类中心漂到很远的位置，会导致：

- 聚类结构不稳定
- 演示出来的路线片区不自然
- depot 视角下的业务含义变弱

所以项目实现的是一个 **ConstrainedKMeans**，不是普通 K-Means。

---

## 5. ConstrainedKMeans 的核心思想

类定义在：

- `backend/app/core/algorithms/kmeans.py`

它比普通 K-Means 多了两层业务逻辑：

1. **分配时考虑容量**
2. **更新中心时考虑离 depot 的最大距离**

### 5.1 距离度量：Haversine，而不是欧氏距离

项目没有直接拿平面欧氏距离算经纬度，而是使用：

- `haversine_distance()`
- `haversine_vectorized()`

Haversine 是球面距离公式，适合经纬度坐标。

它衡量的是：

> 地球表面两点之间的球面最短弧长

为什么这里要用它？

因为即使这是个演示项目，也还是在处理真实经纬度。相比直接拿经纬度差值做欧氏距离，Haversine 更合理。

### 5.2 初始化：不是全图随机，而是围绕站点初始化

函数：

- `initialize_centroids_around_depot(depot, k, radius=5.0)`

它做的事是：

1. 以 depot 为中心
2. 在半径约 `5km` 范围内
3. 随机生成 `k` 个初始中心

这对应一个非常强的业务先验：

> 配送任务本来就是围绕站点发散出去的

所以项目没有把初始中心撒到全局，而是有意让它们一开始就“围着站点展开”。

这个初始化的好处：

- 更符合配送问题的几何直觉
- 初始聚类更稳定
- 更容易得到围绕 depot 的片区结构

### 5.3 主循环仍然是 K-Means 骨架

`fit()` 的流程仍然是标准 K-Means 的 4 步：

1. 初始化中心
2. 分配点
3. 更新中心
4. 判断是否收敛

但这里第 2 步和第 3 步都被改造了。

## 6. 分配步骤：容量约束是怎么加进去的

关键函数：

- `_assign_points_capacitated()`

这部分是 ConstrainedKMeans 最值得你仔细读的地方。

### 6.1 它不是“一个点直接找最近中心”这么简单

算法先构造一个距离矩阵：

```text
dists[i][j] = 第 i 个包裹 到 第 j 个聚类中心 的距离
```

然后对每个包裹点，把所有 cluster 按距离从近到远排序：

```text
sorted_indices[i] = [最喜欢的 cluster, 第二喜欢的 cluster, ...]
```

这里的“喜欢”就是“距离更近”。

### 6.2 它先算一个 regret，再决定谁优先分配

项目没有直接按包裹顺序逐个塞 cluster，而是先计算 **regret（遗憾值）**：

```text
regret = 次优距离 - 最优距离
```

这个量有什么意义？

如果某个点：

- 最优 cluster 很近
- 次优 cluster 很远

那它的 regret 就大。

这表示：

> 这个点一旦不能分给最优 cluster，代价会很高。

所以算法会优先处理 regret 大的点。

这是一个非常典型的启发式思想：

- 先满足“难安置”的点
- 把“去哪都差不多”的点留到后面

### 6.3 真正的容量判断发生在这里

对某个点，算法按它的偏好顺序尝试 cluster：

```python
if current_loads[cluster_idx] + point_weight <= capacities[cluster_idx]:
    分进去
```

也就是说，一个点只有在“不超载”的情况下，才允许被分到某个 cluster。

这就把：

- 包裹重量 `weights`
- 快递员容量 `capacities`

显式地加入了聚类过程。

### 6.4 如果首选 cluster 满了怎么办

那就尝试第二喜欢的、第三喜欢的……

也就是说，这个分配不是硬绑最近中心，而是：

> 最近优先，但要服从容量约束

### 6.5 如果所有 cluster 都装不下怎么办

代码最后还有一个 fallback：

```python
remaining = capacities - current_loads
best_fallback = argmax(remaining)
```

它会把这个点分给“剩余容量最多”的 cluster，即使这会超载。

这说明当前项目的容量约束从严格意义上说是：

- **尽量满足**
- **必要时允许违规，以换取流程继续**

这不是严格可行解求解器，而是一个工程启发式。

它的立场不是：

> 没有严格可行解就直接失败

而是：

> 尽量给一个最合理的近似结果

### 6.6 为什么项目还能大多数时候避免超载

因为演示数据生成逻辑会尽量保证：

- 总包裹重量 < 总可用容量

所以这个 fallback 理论上存在，但在正常样本下不应该频繁触发。

## 7. 更新中心：为什么要加 depot 距离约束

关键函数：

- `update_centroids_with_constraint()`

普通 K-Means 的更新方式是：

> 某个 cluster 的新中心 = 该 cluster 所有点的均值

这个项目先也这么算：

```python
centroid_lat = mean(cluster_points[:, 0])
centroid_lon = mean(cluster_points[:, 1])
```

但随后会做一个检查：

```python
dist_to_depot = haversine_distance(depot, centroid)
```

如果这个中心离 depot 超过了 `max_distance_from_depot`，就把它拉回边界上。

### 7.1 这个约束限制的不是“点”，而是“中心”

这点非常重要。

当前实现并不会：

- 删除远点
- 阻止远点加入 cluster

它限制的是：

> 聚类中心不能跑得离 depot 太远

所以这个约束更像是对“片区中心形态”的控制，而不是对单个包裹配送范围的硬裁剪。

### 7.2 为什么这样做

因为项目希望聚类保持“围绕站点展开”的业务形态。

如果中心可以任意漂移，可能会出现：

- 某个 cluster 的中心离 depot 非常远
- K-Means 逐渐偏向只看局部密度，不再体现站点约束

而加入这个限制后，片区结构会更像“从站点辐射出去的配送区域”。

### 7.3 这其实是一种人为先验

数学上更纯的 K-Means 不会这样做。

这里相当于主动加入了业务先验：

> 合理的配送片区，应该与 depot 保持某种可接受的几何关系。

这就是为什么这个算法虽然叫 K-Means，但本质上已经是一个“业务特化版聚类器”。

## 8. K-Means 阶段最终产出了什么

`ConstrainedKMeans.fit()` 完成后，最重要的输出是：

- `self.labels`
- `self.centroids`
- `self.inertia`

其中服务层真正使用的是：

```python
clusters = kmeans.get_clusters(recipient_coords)
```

返回格式类似：

```python
{
  0: [0, 5, 9, 12],
  1: [1, 2, 7],
  2: [3, 4, 6, 8, 10]
}
```

它的含义不是路线本身，而是：

> 第几个 cluster 里包含哪些包裹索引

这一步完成后，问题就被改写成多个更小的问题：

- cluster 0 内部怎么排顺序？
- cluster 1 内部怎么排顺序？
- cluster 2 内部怎么排顺序？

于是就进入第二阶段。

## 9. 第二阶段：为什么要把每个 cluster 当成 TSP

当某个 cluster 内的包裹已经确定后，这时该快递员要做的事就很像经典 TSP：

- 从 depot 出发
- 访问 cluster 内所有点
- 回到 depot
- 希望总距离尽量短

当然，真实配送不一定要回 depot，也不一定完全等价于 TSP，但在这个项目里，它被简化成了：

> 一个固定起终点为 depot 的闭环路径排序问题

这就是 `GeneticAlgorithmTSP` 的任务。

代码在：

- `backend/app/core/algorithms/genetic.py`

## 10. GeneticAlgorithmTSP 的编码方式

### 10.1 染色体是什么

在这个项目里，一条染色体就是一个排列。

例如：

```python
[2, 0, 3, 1]
```

表示：

- 先访问 cluster 中索引 2 的点
- 再访问索引 0
- 再访问索引 3
- 最后访问索引 1

注意它不是直接存经纬度，而是存“点的顺序”。

### 10.2 为什么排列编码很自然

因为 TSP 的本质就是：

> 对同一组点找一个访问顺序

所以用排列做编码非常自然：

- 每个点必须出现一次
- 不能重复
- 不能遗漏

顺序本身就是解。

## 11. 适应度函数：它真正优化的是什么

关键函数：

- `_fitness(chromosome, addresses, depot)`

路径成本计算方式是：

```text
depot -> addresses[chromo[0]] -> ... -> addresses[chromo[-1]] -> depot
```

总距离越小越好。

但遗传算法通常是“适应度越大越好”，所以这里做了一个倒数：

```python
fitness = 1 / (total_distance + 1e-6)
```

这意味着：

- 路线越短，fitness 越大
- 路线越长，fitness 越小

你可以把它理解成：

> 项目在用“距离的倒数”作为生存竞争指标

### 11.1 为什么这里仍然使用 Haversine

因为项目当前没有接入真实路网距离矩阵。

所以无论在聚类阶段还是 TSP 阶段，它优化的都是：

- 经纬度球面直线距离近似

这会让结果偏“路线排序合理”，而不是“导航路径绝对真实”。

## 12. 初始化种群：从很多随机顺序开始

函数：

- `_initialize_population(num_cities)`

做法很简单：

1. 构造 `[0, 1, 2, ..., n-1]`
2. 每次随机打乱
3. 生成很多个体

这就形成初始种群。

如果 `cluster` 内有 `n` 个点，那么每个个体都是这 `n` 个点的一个排列。

### 12.1 这里没有用贪心初始解

当前实现并没有做：

- 最近邻初始化
- Clarke-Wright 初始化
- 插入式初始化

它完全从随机群体开始，然后靠进化过程逐渐找到更好的顺序。

好处是代码简单。

代价是：

- 初始解质量可能一般
- 更依赖后续迭代和局部搜索

## 13. 一代 GA 里到底发生了什么

`solve()` 的主循环可以拆成 6 个动作。

### 13.1 动作一：评估整个人群

对每个个体计算 fitness。

这相当于在问：

> 当前这一批候选路线里，谁更短？

### 13.2 动作二：找到当前最优个体

找出当代最好的一条路线。

这是“当前最优”，不一定是“历史最优”。

### 13.3 动作三：对当前最好解做 2-opt 局部搜索

这是当前实现非常关键的增强点。

它不是纯粹只靠遗传操作，而是：

> 先用 GA 找到一个还不错的解，再用 2-opt 局部修补它

2-opt 的思想是：

- 在路径里选一个区间
- 把这个区间反转
- 如果路径更短，就接受

这很适合去掉路径中的“明显交叉”和“局部绕路”。

所以当前项目其实是一个：

> GA + 2-opt 的混合启发式

### 13.4 动作四：更新全局最优

如果本代最好解比历史最好解更好：

- 更新 `best_chromosome`
- 更新 `best_fitness`
- 重置停滞计数器

### 13.5 动作五：如果长期没进步，提高变异率

如果连续很多代都没有改进，代码会提高当前变异率：

```python
current_mutation_rate = min(0.5, current_mutation_rate * 1.5)
```

这叫自适应变异。

背后的直觉是：

- 长时间没进步，说明种群可能陷入局部最优
- 这时要增加扰动，鼓励跳出去

### 13.6 动作六：产生下一代

下一代由这些机制构成：

- 精英保留
- 锦标赛选择
- 顺序交叉 OX1
- 交换变异

下面分别解释。

---

## 14. 精英保留：为什么要先把最好的留下

当前实现先把 fitness 最好的若干个体直接复制到下一代。

这叫 **Elite Retention**。

作用很简单：

- 防止优秀解在交叉变异中被破坏
- 保证种群质量不会突然退化得太厉害

这相当于告诉算法：

> 已经找到的好路线，至少先保住一部分。

---

## 15. 锦标赛选择：父代怎么选

函数：

- `_tournament_selection()`

做法是：

1. 随机抽几个个体
2. 让它们比 fitness
3. 选最好的当父代

这比“按全局概率轮盘赌”更简单，也更稳定。

它的效果是：

- 优秀个体更容易被选中
- 但普通个体也不是完全没机会

这样能保持一定竞争压力，又不至于完全失去多样性。

---

## 16. OX1 顺序交叉：为什么适合 TSP 排列编码

函数：

- `_order_crossover(parent1, parent2)`

排列编码最大的问题是：

- 不能像普通二进制串那样随便拼
- 否则会出现重复点、漏点

所以 TSP 常用专门的交叉算子。

当前项目使用的是 **OX1（Order Crossover）**。

核心思想：

1. 从父代 1 里截取一个子序列保留下来
2. 剩下的位置按父代 2 的相对顺序补齐

这样生成的孩子仍然是一个合法排列：

- 不会重复
- 不会漏点
- 同时保留了父代的部分顺序信息

这非常适合“访问顺序”类问题。

---

## 17. 交换变异：为什么足够简单但有效

函数：

- `_swap_mutation()`

操作很简单：

1. 随机选两个位置
2. 交换它们

例如：

```text
[0, 1, 2, 3, 4] -> [0, 3, 2, 1, 4]
```

对 TSP 来说，这是一种非常标准的轻量级扰动。

它的优点：

- 简单
- 不会破坏排列合法性
- 能提供局部探索能力

缺点：

- 扰动幅度有限
- 需要配合交叉和 2-opt 才更有效

---

## 18. 为什么还要单独做 2-opt

如果只有 GA，也能优化，但往往会遇到一个问题：

- GA 擅长全局搜索
- 但对“局部微调”不如专门局部搜索高效

例如，一条路线中可能只有一小段顺序不合理。GA 靠随机交叉变异去碰中这件事，不一定快。

而 2-opt 非常擅长处理这种局部问题。

所以项目采用：

- **GA 负责大范围搜索**
- **2-opt 负责局部精修**

这是一种常见的混合策略。

如果你以后继续优化这个项目，这一层是非常值得扩展的：

- 可以对不止当前最优个体做 2-opt
- 也可以做 3-opt
- 也可以引入更复杂的局部邻域搜索

---

## 19. GA 阶段最终产出了什么

GA 最终返回：

```python
best_route_indices, fitness_history
```

其中：

- `best_route_indices` 是点访问顺序
- `fitness_history` 是每代最好适应度的历史

当前服务层真正拿来用的是：

- `best_route_indices`

它会把这个顺序映射回包裹对象，构造一条完整路径：

```text
depot -> package A -> package B -> ... -> depot
```

然后计算总距离并写入 route。

---

## 20. 两阶段是怎么在服务层里接起来的

理解算法最重要的一步，是把“聚类输出”与“GA 输入”连接起来。

在 `DispatchService` 里，这个衔接过程是：

### 20.1 K-Means 先输出 cluster

格式：

```python
clusters = {
  cluster_idx: [package_index_1, package_index_2, ...]
}
```

### 20.2 对每个 cluster 取出本地子问题

```python
cluster_packages = [packages[i] for i in pkg_indices]
cluster_coords = [recipient_coords[i] for i in pkg_indices]
```

也就是说，对 GA 来说，它根本不关心全局所有包裹，只关心：

- 这个 cluster 里的点
- depot

### 20.3 每个 cluster 独立调用一次 GA

```python
ga.solve(cluster_coords, depot_coord, progress_callback=...)
```

因此当前项目不是“一个大 GA 求整个全局路线集合”，而是：

> 一个 K-Means + 多个小 GA

这就是它可扩展、可讲解、也比较容易运行的原因。

---

## 21. 这个项目为什么能“实时看到优化中的路径”

这是服务层做的一项非常演示友好的设计。

在调用 GA 时，传入了：

```python
progress_callback=ga_progress_callback
```

GA 每隔 5 代会回调一次，而服务层在回调里会：

1. 根据当前最优顺序构造临时路径
2. 计算临时总距离
3. 写入 `route.geo_json`
4. 每隔 20 代提交一次数据库

所以数据库中的 route 在优化过程中不是空的，而是不断更新的。

这就让前端轮询能够看到：

- 折线先出现
- 迭代代数变化
- 总距离逐渐稳定

从算法角度看，这不是求解质量提升的关键，但从“可观测性”角度看非常重要。

---

## 22. 结果在数据库里是怎么表达的

项目最终不会只保留一个“最优顺序数组”，而是把它转成一个更适合前端消费的数据结构。

每条 `DeliveryRoute.geo_json` 会保存：

- `coordinates`
- `cluster_center`
- `total_distance_km`
- `package_count`
- `total_weight`
- `color`
- `status`
- `generation`
- `packages_ordered`

其中最关键的是：

### 22.1 `coordinates`

它是路线几何线段：

```text
[depot, 包裹1, 包裹2, ..., depot]
```

但注意写入时被转成了：

- `[lon, lat]`

这是为了地图渲染格式，而不是算法计算格式。

### 22.2 `packages_ordered`

它保留了实际顺序下的包裹信息。

这意味着前端不仅能画线，还能标出：

- 第 1 站
- 第 2 站
- 第 3 站

换句话说，GA 的“排列解”被转成了可视化的路线表达。

---

## 23. 这套实现到底近似了什么

这是理解原理时非常关键的一点。

这个项目并没有直接求完整 CVRP，而是在做如下近似：

### 23.1 近似一：先聚类再排序

它假设：

> 只要先把包裹分成合理片区，片区内再做 TSP，整体就会足够好。

这通常成立，但不保证全局最优。

因为现实中可能存在：

- 某个点在空间上更接近 cluster A
- 但如果从全局路线角度考虑，它放进 cluster B 更优

当前两阶段方法无法表达这种跨 cluster 的全局交换优化。

### 23.2 近似二：容量在聚类阶段处理，但路线阶段不再重新考虑容量

GA 只优化访问顺序，不再处理容量。

这等于默认：

> K-Means 阶段已经把容量问题解决掉了

如果聚类阶段有误差，GA 不会修复这个问题。

### 23.3 近似三：使用直线距离代替道路距离

项目优化的是：

- 球面直线距离

而不是：

- 道路里程
- 行驶时间
- 路况成本

所以它更像“几何意义上的优路线”，而不是“真实交通意义上的优路线”。

### 23.4 近似四：快递员与 cluster 的绑定很粗糙

当前 cluster 创建后，route 上的 `courier_id` 直接按索引绑定：

```python
courier = couriers[cluster_idx]
```

这意味着系统没有进一步求：

- 哪个快递员更适合哪个 cluster

所以严格来说，当前实现甚至可以分成三层问题：

1. cluster 生成
2. cluster 与 courier 匹配
3. cluster 内路径排序

而当前项目把第 2 层简化掉了。

## 24. 这套实现的优点到底是什么

### 24.1 代码结构清楚

你可以很明确地把算法拆成两个模块去读：

- `ConstrainedKMeans`
- `GeneticAlgorithmTSP`

学习成本相对低。

### 24.2 业务含义强

先分片区、再做片区内路线，这很符合人类调度直觉。

所以即使不是最优，结果通常“看起来合理”。

### 24.3 可视化友好

因为每个 cluster 都天然对应一条路线，所以：

- 地图展示直观
- 颜色区分容易
- 中间结果也容易解释

### 24.4 对演示项目很合适

相比完整 VRP 求解器，这套方案：

- 实现成本低
- 可运行性强
- 可讲解性强
- 修改门槛低

## 25. 它的局限和潜在改进点

如果你想更深入理解原理，必须同时理解它的边界。

### 25.1 不是全局最优

这是最大的事实。

一旦先分 cluster，再单独优化内部顺序，就已经放弃了全局联合优化。

### 25.2 聚类目标和最终路线目标并不完全一致

K-Means 优化的是：

- 点到中心的紧凑性

但最终真正关心的是：

- 从 depot 出发再回 depot 的路线长度

两者相关，但不是同一个目标函数。

所以你可能会看到某些 cluster：

- 几何上看很紧凑
- 但实际闭环路线不一定最好

### 25.3 容量约束不是完全严格

在极端情况下，它允许 fallback 到超载 cluster。

这说明它是一个“尽量可行”的启发式，而不是严格的可行解保证器。

### 25.4 没有时间窗、优先级、路况

真实配送常见的约束包括：

- 时间窗
- SLA 优先级
- 禁行路段
- 电动车续航
- 上下班时间

当前项目都没有处理。

### 25.5 没有真实道路图

所以它算的是“几何路线”，不是导航路线。

## 27. 用一句话重新总结这套算法

如果只允许一句话来概括这个项目的路径规划实现，我会这样说：

> 它把一个近似 CVRP 的末端配送问题拆成“带容量与站点约束的空间聚类”和“cluster 内的 TSP 顺序优化”两个子问题，分别用 Constrained K-Means 与 Genetic Algorithm + 2-opt 求解，再把结果拼装成可视化路线。

如果再拆成更白话的两句：

- **K-Means 决定谁送哪些包裹**
- **GA 决定这些包裹按什么顺序送**

这就是这个项目路径规划算法的核心。

## 28. 给你一个真正有用的学习抓手

如果你接下来要自己读源码，建议你始终带着这 4 个问题去看：

### 问题 1：当前这段代码是在做“分配”，还是在做“排序”？

如果是在 `kmeans.py`，它主要在做分配。

如果是在 `genetic.py`，它主要在做排序。

### 问题 2：当前这段代码优化的目标是什么？

- K-Means：空间紧凑 + 容量尽量满足 + 中心不离 depot 太远
- GA：路线总距离尽量短

### 问题 3：当前这段代码的输入输出是什么？

这是把抽象原理落到代码实现的关键。

### 问题 4：这里是在求“更真实”，还是求“更容易演示”？

这个项目很多设计选择都偏后者。

只要你用这个视角看，就会很容易理解为什么作者这样写。
